## Qué se hizo

- `src/domain/agenda/turno.ts`: tipo `Turno` completo (`estado` `reservado` al crear, `senado: false`, `esSobreturno: false`, `origen`, `creadoPor`, `creadoEn`). Los changes siguientes no deberían editarlo.
- `src/domain/agenda/validarNuevoTurno.ts` (puro): calcula `fin` desde la prestación (RN-AG-11/03), exige alineación a 15' (RN-AG-03), franja del profesional y ausencia de bloqueos (RN-AG-04), sin solapamiento por profesional y sillón (RN-AG-02, semántica `[inicio, fin)` de RN-AG-01) ni por paciente (RN-AG-05); ignora cancelados (RN-AG-10). Orden fijo: alineación → franja → bloqueo → profesional → sillón → paciente; corta en el primer error e informa el conflicto de inicio más temprano. Recibe la lista de turnos ya filtrada (C-04 la reutiliza excluyendo el propio turno).
- `src/application/agenda/crearTurno.ts`: permiso por rol (recepción, admin y paciente crean; odontólogo y sin rol → 403), carga entidades (id inexistente → 400), valida, guarda y audita `accion: 'crear'` (RN-AU-01). Las altas rechazadas no auditan.
- `src/api/routes/turnos.ts`: `POST /api/turnos` (201 / 400 / 403 / 409) y `GET /api/turnos?desde&hasta&profesionalId&sillonId`.
- Cuerpo del 409: `{ error: { tipo: "regla", regla, mensaje, dimension?, conflicto?: { turnoId } } }`. `dimension` vale `profesional`, `sillon` o `paciente`; RN-AG-03/04 no llevan `dimension` ni `conflicto`.
